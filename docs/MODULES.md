# Modules

One row per module. "Side" is the `FeatureModule.Side` this module declares (`Server` = dedicated
server only, `Client` = player only, `Both` = runs on either half). "Hot-reload" describes whether
a live edit to the module's cfg entries takes effect without a server/game restart — every entry
bound with `BindSynced`/`BindLocal` (or wired with `Watch()`) is pushed through `OnConfigChanged`
automatically; the exceptions are called out. "Needs real players" says whether the module's
actual effect can be verified with 0 players connected (self-tests, static config plumbing,
solo-safe patches) or needs at least one real client connection to observe (per-peer telemetry,
budgets, compression handshake, map sharing, etc.) — the module still *loads* and *patches*
with 0 players either way.

All modules are discovered by reflection (see `src/Plugin.cs` `DiscoverModules()`); there is no
registration list to keep in sync. Every module's own `Enabled` toggle lives in its own `[Section]`
and is itself hot-reloadable (a live edit updates `EnabledCfg.Value` immediately), but note that
disabling a module that already installed its Harmony patches does **not** unpatch it — only a
process restart fully removes an already-applied module's patches; only the module's *behavior
gates* (the `internal static bool Active` / `IsActive` checks in patch bodies) turn off live.

The tick then watches that ZDO's `DataRevision`: the owner's authoritative answer arrives as a ZDO update and bumps it, so the first bump is the moment the hit registered; a ZDO that disappears counts as registered, anything past 3 s is a timeout. **(c) Ownership churn (client):** a postfix on `ZDO.SetOwner` (vanilla only calls through on a real change) counts transfers within 30 m of the local player. **(d) ZDO churn by prefab (server, 0.5.2):** "140–160 kB/s and ~800 ZDO updates/s to each player near the base" is the symptom; this names the cause. The server logs one line per client per interval, puts the same fields in StatsLog, and repeats them in `ss.lag`; reports from a peer that is not ready are ignored, an oversized package is dropped unread, and a client without the mod never sends. **Session-edge filter (0.5.2):** the first real data put every multi-second "RTT" at a join (client loading the world) or a leave (client saving and quitting) — not latency. Every probe sent within `EdgeIgnoreSec` of a peer becoming ready, and every probe once the server knows the peer is going away (`ZNet.Disconnect`, or a socket already reporting disconnected), is dropped whole: no RTT, no jitter, and an unanswered one is never charged as loss (it is counted as `edgeDropped`). If nobody needs it after that, the ping/report RPCs themselves are removed in a later release. ## Transpiler coexistence (0.5.2, issue #2)

Five modules work by swapping a hardcoded vanilla literal for a call: SendBudget and ClientNet
(`ZDOMan.SendZDOs`' two `10240`s and its `2048`), CreateBudget (`ZNetScene.CreateObjects`' `10`),
OwnershipRelease (`ZDOMan.ReleaseZDOS`' `2f`) and SmoothMotion (`ZSyncTransform.SyncPosition`'s
`0.2f`/`2f`). Each asserts the exact number of literals it found, so that a Valheim update which
rewrites the method makes the module refuse to patch instead of quietly doing the wrong thing —
that assertion has caught every game patch so far and it has not been relaxed.

What it could not see is that **Harmony chains transpilers**: when two mods transpile the same
method, the second one is handed the *first one's output*, not the game's IL. Several networking
mods rewrite exactly the same send-budget constants we do, so after one of them has run our scan
finds `0` of them — indistinguishable, by counting alone, from Iron Gate having changed the method.
0.5.1 and earlier threw there, reported `FAILED`, and blamed the game.

Since 0.5.2 each of those modules asks Harmony (`ILUtil.OtherTranspilersOn`, i.e.
`Harmony.GetPatchInfo(target).Transpilers`) who else is already on its target *before* it patches.
If another owner is, the module installs nothing, logs one line —

```
[SendBudget] another mod already changed ZDOMan.SendZDOs (owners: com.example.OtherMod) -
SendBudget left off so the two do not fight; set [SendBudget] Enabled=false to silence this
```

— and reports the status **`disabled(conflict)`** in the module summary (alongside `applied`, `disabled(IL mismatch)` (0.5.3: nobody else on the method, but its IL is not one SendBudget recognises),
`disabled`, `disabled(side)` and `FAILED(reason)`). The other mod keeps its patch and its settings;
ours simply stays out of the way, and every other SmoothServer module is unaffected. The same guard
runs inside the transpiler itself for the late case — a third mod patching the method *after* us,
which makes Harmony re-run the whole chain over their output — and there it hands the instruction
list back untouched rather than throwing. AdaptiveBudget applies its per-peer number through
SendBudget's call site, so its summary line says `no effect: SendBudget is disabled(conflict)`
rather than implying a budget that is not reaching the game.

This is the same courtesy Compression already extends to BetterNetworking (which it refuses to
patch alongside, for the same "two mods, one send path" reason). If you want SmoothServer's budget
instead of the other mod's, uninstall the other mod; if you want theirs, set the section's
`Enabled=false` and the warning goes away.

## Profiles (`[Profiles]`, not a module)

| Setting | Default | Notes |
| --- | --- | --- |
| `Profile` | `Default` | `Default` / `FastLink` / `Custom`. **Synced** — the server dictates it. A preset, not a feature: it writes a fixed table of values into ten settings that already exist (`[SendCadence] SendHz`, `[AdaptiveBudget] CeilingBytes`/`FloorBytes`, `[SteamRates] SendRateMax`, `[Client] HighWaterBytes`/`SendRateMaxBytesPerSec`, `[Compression] Enabled`, `[LowLatency] NagleMicros`, `[FrameRate] TargetFrameRate`, `[CreateBudget] MaxCreatedPerFrame`) at load, on every profile change, and after every live cfg reload. `Default` forces those keys to their shipped defaults; `FastLink` to the LAN-feel set; `Custom` overrides nothing. Every affected key repeats this in its own cfg description. Hot-reloadable in both directions; `tools/cfg.py preset ss fastlink\|default\|custom` flips it. |

Precedence: on `Default` and `FastLink` the profile beats the file for those ten keys, and
re-asserts itself (with a log line) over a hand edit — hand-tuning belongs on `Custom`.
The new value is written into the cfg file, so what you read there is always what is running.
